Status: plan. Record 0106 closed at `f0e7aea` + `1eecbf1`. The 0107 plan is committed locally as `e869ea5`; its implementation is paused in `stash@{0}` (`rnx 0107 validity merge impl, paused for v2 parity reframe`). Do not apply or discard the stash in this record.

## Target and definition

The user wants the **Rust Polars API** available to Rune users as fully as practical, with scriptable, fluid mappings rather than a Python-shaped facade. Python Polars may suggest ergonomics, but its API is **not** a denominator, compatibility contract, or required oracle. A 90% Rust-API coverage level would be a major win; 100% remains an aspiration, not permission to hide difficult public Rust callables. Avoid a plan/implementation record per method: follow-on records should cover a shared mapping or execution class, often across many owners.

The v2 source is the Rust workspace at Polars's Python `py-2.0.0-rc.2` tag, immutable commit `da47b7405f0e2d188e71cce7c2d588c695f4098d`. There is no published Rust Polars 2.0 crate. The 0074 probe used this commit and found that an earlier generator compiled against it, but that probe did not exercise the current 0106 generator or establish parity with the Python wheel's feature set. When a stable `py-2.0.0` tag appears, update the pin and rerun this baseline as a separate measured change. The 0.55.2 target may be retired once the v2 build and oracle baseline work; preserve its historical commits and evidence.

Every quoted coverage percentage must name its denominator. Report at least three views side by side: (1) **all public reachable Rust callables** at the pinned workspace and feature set, including difficult trait/unsafe/async forms; (2) **script-applicable callables**, with every exclusion explicitly listed and justified by a documented Rune or safety contract; and (3) **value-tested callables** that have a direct Rust behavioral comparison. Report distinct callable identities separately from emitted bindings and aliases. Do not treat a Rust-internal-looking public method as irrelevant merely because Python does not expose it. Track functional capability families as an additional prioritization view, not as a replacement for callable accounting.
